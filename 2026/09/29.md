## わかったこと
- Go のレシーバ
  - 型（構造体など）に関数を紐付けるための仕組み。型に紐付いた関数を「メソッド」と呼ぶ。
  - `func (r 型名) メソッド名()` の `(r 型名)` の部分がレシーバ。
  - レシーバの有無で、呼び方が変わる。
    - レシーバなし：「関数」と呼ぶ。`関数名()` や `パッケージ名.関数名()` で呼び出す。
    - レシーバあり：「メソッド」と呼ぶ。`値.メソッド名()` で呼び出す。
  - レシーバには2種類ある。
    - 値レシーバ：`(c Chapter)`
      - 呼び出し元の値のコピーを受け取るので、中で書き換えても元の値は変わらない。
    - ポインタレシーバ：`(c *Chapter)`
      - 呼び出し元の値の場所（ポインタ）を受け取るので、中で書き換えると元の値も変わる。
  - メソッド内でレシーバを使わないときは、`func (Chapter) TableName() string` のようにレシーバの変数名(`c`)を省略できる。

- レシーバの学習を通してわかったこと（Chapter 作成機能の実装）
  - レシーバ（インフラ層）とインターフェース（ドメイン層）の関係
    - ドメイン層のインターフェースは、`Save` の形（メソッド名・引数の型・戻り値の型）だけを決める。（コード例1）
    - インフラ層は、ポインタレシーバで同じ形の `Save` を `chapterRepository` に紐付ける。これにより、`*chapterRepository`（ポインタ）がインターフェースを満たす。（コード例2）
    - `&` を付ける理由：`Save` がポインタレシーバなので、ポインタ（`&chapterRepository{}`）にしないとインターフェースを満たさない。（コード例2）
    - `*` を付けない理由：インターフェースへのポインタ（`*domain.ChapterRepository`）はメソッドを持たない型になり（メソッドが生えない）、`Save` が呼べなくなる。（コード例2）

  - コード例
    - Chapter のリポジトリ
      - コード例1：ドメイン層（約束）
        ```go
        // domain パッケージ
        type Chapter struct {
            Title string
        }

        // インターフェース（Save を持つことを約束する）
        type ChapterRepository interface {
            Save(c *Chapter) error
        }
        ```

      - コード例2：インフラ層（約束の実装）
        ```go
        // postgres パッケージ
        type chapterRepository struct{}

        // 戻り値の型（ドメイン層のインターフェース）には * を付けない
        func NewChapterRepository() domain.ChapterRepository {
            // 構造体の値には & を付ける
            return &chapterRepository{}
        }

        // ポインタレシーバで Save を実装する
        func (r *chapterRepository) Save(c *domain.Chapter) error {
            return nil
        }
        ```

## 感じたこと
- インターフェースは、実装する側（インフラ層）が持つべきメソッドを定める「約束」だと、イメージできるようになった。
  - 例）ドメイン層のインターフェースに `Save(c *Chapter) error` と書かれていれば、インフラ層ではメソッド名・引数の型・戻り値の型を同じ形にして `Save` を作る必要がある。
- 今後、メソッドを実装する際は、インターフェースの定義どおりにメソッド名・引数の型・戻り値の型をそろえることと、レシーバの種類（値かポインタか）を意識したい。
