## わかったこと
- 依存性逆転の原則（DIP）と依存性の注入（DI）
  - 疑問
    - usecase も domain も infra を import していないのに、なぜ usecase から infra の保存処理が動くのかがわからなかった
  - わかったこと
    - usecase が知っているのは domain の interface 型だけで、どのリポジトリ実装が使われるかは知らない
    - main で infra のリポジトリ実装を作成し、usecase に渡している（DI：依存性の注入）
    - そのため、コード上は domain の interface 型のメソッドを呼んでいるが、実行されるのは渡された infra のリポジトリ実装
    - 依存性逆転の原則（DIP）では、処理の向きは変わらず、依存の向きだけが変わる
      - DIPなし
        - 依存：usecase → domain → infra
        - 処理：usecase → domain → infra（domain のリポジトリが infra の DB 処理を直接呼ぶ）
      - DIPあり
        - 依存：usecase → domain ← infra
        - 処理：usecase → infra（domain の interface 型を通して、infra の実装が実行される）
  - 依存と処理の向きの違い
    - 細線：依存の向き
    - 太線：処理の向き
    
      ```mermaid
      flowchart TB
          MAIN["main<br>（組み立て役）"]
          H["ハンドラー層<br>（interface/http）"]
          U["ユースケース層<br>（application）"]

          subgraph INFRA["インフラ層（infra）"]
              IMPL["リポジトリ実装<br>chapterRepository<br>（構造体）"]
          end

          subgraph DOMAIN["ドメイン層（domain）"]
              IF["リポジトリインターフェース<br>ChapterRepository<br>（interface）"]
          end

          DB[("DB<br>PostgreSQL")]

          %% 依存：細線
          H -->|"依存（import）"| U
          U -->|"依存（import）"| IF
          IMPL -->|"依存（import）"| IF

          %% 処理：太線
          H ==>|"① 呼び出す"| U
          U ==>|"② Save() を呼び出す"| IMPL
          IMPL ==>|"③ SQL（INSERT）を実行"| DB

          %% DI：点線
          MAIN -.->|実装を渡す（DI）| U
      ```

## 感じたこと
- 「処理が動くなら、そのコードを import しているはず」と、依存と処理の向きを同じものだと考えていた
- import（依存）は型を知るためのもので、実際に動く処理は実行時に渡された実装で決まる、と分けて考えたことで、import していないのに処理が動く理由が理解できた
