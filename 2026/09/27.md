## わかったこと
- GitHub の PR のマージ方法
    - 主に以下の3種類がある（参考：https://docs.github.com/ja/pull-requests/reference/pull-request-merges）
    1. Merge commit
        - feature のコミットをそのまま main に取り込む（コミットID・日時は維持）
        - main と feature を統合するマージコミットが追加される
    2. Squash and merge
        - feature の複数コミットを1つにまとめて main に取り込む
        - 元のコミットは main の履歴に残らないので、履歴をシンプルにできる
    3. Rebase and merge
        - feature の各コミットを main の先頭に作り直して追加する
        - 親コミットが変わるため、新しいコミットIDになる（Commit Date も更新される）
        - マージコミットを作らず、履歴を一直線にできる

- PR 作成からマージまでの流れ
  - ローカル環境での作業
    ```bash
    # ブランチ作成
    git switch -c feature
    # ワーキングツリーの変更をインデックスに追加
    git add .
    # インデックスの内容をローカルリポジトリにコミット
    git commit -m "feat: 変更内容"
    # ローカルリポジトリのコミットをリモートリポジトリ（GitHub）にプッシュ
    # マージコミットが追加されるだけなので、通常の push で PR に反映する
    git push origin feature
    ```

  - GitHub での作業
    - PR を作成し、レビュー完了後に Merge / Squash / Rebase のいずれかでマージする

- コンフリクト
    - 同じファイル・同じ箇所を複数人が変更した場合などに、Git が自動で統合できない状態
    - 競合箇所を確認し、手動で修正する

- コンフリクトの解消方法
    1. Merge で解消（main を feature に取り込む）
        ```bash
        git switch feature
        git merge main
        # コンフリクトを修正後
        git add .
        git commit
        git push origin feature
        ```
    2. Rebase で解消（feature を main の先頭に付け替える）
        ```bash
        git switch feature
        git rebase main
        # コンフリクトを修正後
        git add .
        git rebase --continue
        # コミット履歴が変わるため強制 push
        # コミットが作り直され履歴が変わるため、強制 push で PR に反映する
        git push --force-with-lease origin feature
        ```
